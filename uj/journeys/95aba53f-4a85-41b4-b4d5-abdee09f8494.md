# Readable Property Names in Properties Block

## Job Story

**When** я открываю ассет (ems__Task, ems__Project, ems__Area, ims__Concept и др.) в Reading Mode и смотрю на встроенный Obsidian Properties block,
**I want** видеть человекочитаемое имя каждого предиката (например, «Effort Area» вместо `ems__Effort_area`) и кликать по этому имени, чтобы открыть ассет, описывающий предикат,
**so** я понимаю онтологию без знания namespace-нотации и могу изучать schema прямо из UI, не переключаясь на SPARQL.

## Status

**ACTUAL** — implemented in plugin v15.96.0 (`PropertiesLabelPatch`) and verified live against `getting-started-test-vault` on 2026-04-14. Scenarios A/B/C all PASS. The initial v1 implementation had two bugs (case-mismatch on `data-property-key` lookup and frontmatter key corruption via `input.value = label`) that were fixed in a follow-up PR (kitelev/exocortex#2796) using a span-overlay model. `exocortex-logs.txt` shows 0 `[ERROR]` entries during the verification run.

## Preconditions

- Exocortex plugin ≥ v15.94.0 (baseline; implementation bumps to a future version)
- Starter kit ≥ v1.9.0 installed — ships this journey файла + property definitions с человекочитаемыми `exo__Asset_label` (например, «Effort Area», «Effort Status», «Asset Label»)
- Seeded notes in vault:
  - `ems__Effort_area.md` (property def asset) with `exo__Asset_label: "Effort Area"`
  - `ems__Effort_status.md` (property def asset) with `exo__Asset_label: "Effort Status"`
  - `Build API Server.md` with `exo__Instance_class: [[ems__Project]]`, `ems__Effort_status: [[ems__EffortStatusDoing]]`, `ems__Effort_area: [[Development]]`
- Vault state = `seeded`
- Obsidian Properties block рендерится (стандартный Obsidian Source Mode / Reading Mode)

## Scenario A: Properties block shows readable labels

```gherkin
  Given I open "Build API Server" в Reading Mode
  And the Obsidian Properties block is visible above the body
  Then the property row for `ems__Effort_status` displays the label "Effort Status" (not "ems__Effort_status")
  And the property row for `ems__Effort_area` displays the label "Effort Area" (not "ems__Effort_area")
  And the property row for `exo__Asset_label` displays the label "Label" (not "exo__Asset_label")
  And each property name is rendered as a clickable link (visually distinct from raw text)
```

## Scenario B: Clicking a property name opens its definition asset

```gherkin
  Given I open "Build API Server" в Reading Mode
  And the property row for `ems__Effort_status` is visible with label "Effort Status"
  When I click on the "Effort Status" label
  Then a new leaf opens with the property definition asset
  And the opened asset's `exo__Asset_label` равен "Effort Status"
  And the opened asset's `exo__Instance_class` содержит одну из: `exo__StringProperty`, `exo__NumberProperty`, `exo__ObjectProperty`
  And the opened asset is the same file as `ems__Effort_status.md` (or its UUID equivalent)
```

## Scenario C: Fallback for predicates without a definition asset

```gherkin
  Given I open a note that has a property `vendor__Custom_field` with no matching property definition asset in the vault
  And the note is in Reading Mode
  Then the property row renders the raw predicate name `vendor__Custom_field` as fallback
  And no click-to-navigate target is attached (or clicking produces a benign no-op Notice)
  And no error is written to exocortex-logs.txt
```

## Acceptance Gates

### User effort (hard assertions)

| Metric | Max | Measured how |
|---|---|---|
| Clicks to reach property definition asset from an asset row (Scenario B) | 1 | action-log.jsonl counts `left_click` events on the "Effort Status" label → new leaf |
| Keystrokes needed | 0 | No typing required |

### Observable behavior (hard assertions)

- **Scenario A**: for every `ems__Effort_*`, `exo__Asset_*`, `ems__Context_*`, `pn__DailyNote_*` property on a seeded asset, the Properties block row displays `exo__Asset_label` from the property definition asset instead of the raw predicate name
- **Scenario A**: readable label comes from the property definition asset's `exo__Asset_label`, not from `aliases`, not from filename, not from LLM prediction
- **Scenario A**: visual affordance (underline / color) signals the label is clickable
- **Scenario B**: click opens the predicate definition asset in a new leaf (same pattern as wikilink click)
- **Scenario C**: unknown predicate does NOT crash layout, does NOT emit `[ERROR]` in logs, falls back to raw name
- `exocortex-logs.txt` diff contains zero new `[ERROR]` lines for all three scenarios
- Plugin bundle size delta ≤ +5kb (this is a rendering feature, not a framework change)

### Soft informational (NOT a gate)

- Wall-clock overhead per Properties block render — logged in `timings.json`, target < 50ms for 30-property assets, never failure condition

## Failure modes (documented, not assertions)

- Property def asset has `exo__Asset_label` that equals its raw predicate name (e.g., `exo__Asset_label: ems__Effort_area`) → starter-kit must ship human-readable labels; this journey blocks until property defs are cleaned
- Plugin reads `aliases` instead of `exo__Asset_label` → wrong source of truth, returns namespace alias rather than human name
- Plugin cannot find property def asset for a predicate → fallback to raw name (Scenario C), not a regression
- Plugin mutates Obsidian's native Properties DOM and Obsidian resets it on next render → need persistent patch (similar to `PropertiesLinkPatch` / `PropertiesUidCopyPatch` already in plugin)
- Click target binds to wrong file (e.g., an instance instead of the definition) → namespace-to-file resolution bug
- Reading Mode only: Live Preview may not render the patched labels; if so, document as known limitation, do not block
